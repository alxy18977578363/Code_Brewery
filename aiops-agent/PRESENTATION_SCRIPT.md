# 基于 Agent 的智能运维系统技术
## 一、演示定位

- 建议时长：8～10 分钟
- 视频格式：MP4
- 演示地址：`http://127.0.0.1:8000/`
- 核心重点：技术架构、设计思路、个人实现、两个应用场景和界面使用体验

这不是一段连续执行命令的操作录屏，而是一场围绕“为什么这样设计、系统如何工作、用户如何使用”的技术演讲。命令和接口只用于证明环境正常，不占据演讲主体。

1. 使用一键脚本启动 Docker Demo、MySQL、WSL2 FreeAiOps 和 Agent API。
2. 浏览器打开 `http://127.0.0.1:8000/`，确认页面可以自动采集并显示数据。
3. 准备一个正常状态和一个异常状态，异常状态可以通过 Demo 的 `/error` 接口产生。

5. 确认 `.env` 中的模型配置可用，但录制中不打开 `.env`，不展示 API Key。
6. 准备一张系统架构图。流程图和数据链路图使用 Mermaid 绘制后展示。

**屏幕**：项目标题页或网页首页，画面保持简洁。

**讲解**：

> 大家好，我的项目是一个基于 Agent 的智能运维系统。它面向一个具体问题：当微服务出现响应变慢、错误率升高或依赖连接异常时，运维人员需要同时查看指标和日志，才能判断问题到底发生在哪里。
>
> 我的设计目标将数据采集、故障检测、事件管理、根因分析、LLM智能建议和结果展示连接成一条完整链路。系统先回答当前是否异常，再进一步解释可能原因，并把结果呈现给用户。



**屏幕**：展示架构图。

```text
Docker Demo 微服务
        │ 指标 / 日志
        ▼
Python AIOps Agent
        │ 数据校验与标准化
        ▼
规则异常检测 ── 正常 ──> 保存本地历史
        │ 异常
        ▼
FreeAiOps 事件中心 + MySQL
        │ 查询并取回事件
        ▼
根因分析与人工排查建议
        │ 可选
        ▼
OpenAI-compatible / DeepSeek LLM
        ▼
SQLite 历史库 + FastAPI + Web 控制台
```

**讲解**：

> 这张图是整个项目最重要的部分。最上侧是被运维的 Docker Demo 微服务，它提供健康检查、运行指标接口，同时把运行日志写入项目运行目录。
>
> 中间的 Python Agent 是系统的协调中心。它先把指标和日志转换成统一观测快照，再进行格式校验和异常检测。异常检测使用明确规则，因此每个判断都可以追溯到具体指标值、阈值或日志级别。
>
> 正常数据直接保存到项目本地历史库。异常数据通过适配层写入 FreeAiOps。FreeAiOps 在这里承担事件中心的作用，使用 MySQL 保存自己的框架数据。Agent 写入事件后还会再次查询并取回它，确认数据真正经过了事件管理组件。
>
> 取回的事件进入根因分析模块。根因分析把指标和日志放在一起解释。例如数据库连接使用率升高、响应时间变长，同时出现数据库连接超时日志时，系统会把连接池紧张或慢查询作为优先排查方向。
>
> 配置模型接口后，可以把结构化上下文交给  LLM 模型，这里示例使用的是DeepSeek 模型，让模型把分析结果整理成自然语言诊断书。


> 系统实现了两个相互衔接、但职责不同的应用场景。
>
> 第一个是故障检测场景。Agent 接收指标数据，可以附带日志，然后自动判断服务是否异常，输出结构化故障检测报告。报告中不仅有正常或异常标签，还有严重程度、置信度、异常指标、阈值和日志证据。它解决的是“现在有没有故障”。
>
> 第二个是根因分析场景。Agent 把检测结果和 Log、Metric 等多维数据结合起来，分析可能的故障原因，并给出按优先级排列的人工排查或修复建议。它解决的是“故障为什么发生、下一步查什么”。
>
> 这两个场景可以单独使用，也可以连在一起使用。先检测，再解释，是我在系统中采用的基本工作方式。

### 2:20～3:40 第二部分：核心设计与个人实现

**屏幕**：展示架构图中的设计标签、代码目录或关键模块名称，不逐行讲代码。

**讲解**：

> 这个项目的个人设计主要体现在几个方面。
>
> 我把故障检测和根因分析分成两个层次。检测层只负责判断“是否异常”，输出稳定、可解释的证据；分析层负责回答“为什么异常、应该如何排查”。这样既保证检测结果可复现，也让大模型只处理已经整理过的上下文。
>
> 我设计了统一的观测数据格式。CPU、内存、响应时间、错误率、数据库连接和日志都放在同一个观测快照中，后续接口、存储、测试和网页都使用这套结构，避免各模块重复定义数据。
>
> 我实现了 FreeAiOps 适配层。由于当前 FreeAiOps 版本没有专用告警写入接口，我就利用已确认的通用接口保存带唯一编号的事件信封，再查询取回。相同异常指纹去重，避免每秒采集造成事件洪水。

**讲解**：

### 5:10～6:10 第五部分：实时监控界面怎么使用

**屏幕**：进入“实时监控”，保持页面稳定几秒钟。

**讲解**：

> 实时监控页面的第一层信息是当前状态：CPU、内存、磁盘和项目日志数量。用户不需要理解后台接口，只要先看这里，就能知道采集的具体情况。
>
> 服务概览说明数据来自哪个服务、什么时候采集、使用了什么数据源。异常信号区域把检测结论拆成可读线索，例如某个指标当前值超过阈值，或者日志中出现 ERROR。重点是让用户看到判断依据，而不是只看到一个红色的“异常”。
>
> 右侧的事件链路回答数据走到了哪一步：Agent 是否完成采集，异常是否写入 FreeAiOps，事件是否被取回，以及是否调用了 LLM。当 FreeAiOps 离线时，用户不会误以为整个 Agent 都不可用。
>
> 页面支持自动采集、暂停、继续和立即检测。频率选择控制采样速度，不改变检测规则。对于持续出现的同一异常，页面显示已去重，而不是每秒创建一条新事件。

### 6:10～6:50 第六部分：演示一次故障检测

**屏幕操作**：切换到故障检测，点击“填入随机异常案例”或输入一组异常指标，提交检测。

**讲解**：

> 下面演示故障检测场景。这里输入的是一条指标观测，系统会自动完成格式校验和异常判断。为了方便演示，我可以生成一个随机异常案例，每次至少保证有一项指标超过阈值。
>
> 提交后，页面给出故障检测报告。大家可以看到异常标签、严重程度、置信度和具体证据。比如响应时间超过阈值，或者错误率高于设定范围，报告会明确列出当前值和比较阈值。


### 6:50～7:50 第七部分：演示根因分析和 AI 助手

**屏幕操作**：进入“AI 助手”，选择刚才的历史记录，点击常用问题或输入自定义问题。

**讲解**：

> AI 助手不是一个没有上下文的空白聊天框。用户先选择要咨询的历史检测记录，问题就会和具体的服务、指标、日志和检测结果绑定。
>
> 我选择刚才的异常记录，并询问：“请解释这次服务为什么被判定为异常，并给出人工排查顺序。”Agent 会把选中的只读上下文发送给模型，模型返回自然语言诊断。回答可以包含判断依据、可能原因和排查顺序，但不会执行任何命令。
>
> 页面提供常用问题、复制回答和安全边界提示。标题、列表等 Markdown 内容会被渲染成易读格式，用户不需要阅读原始 JSON。
>
> 如果模型没有配置或暂时不可用，页面会明确提示，并保留本地规则分析结果。这样 AI 是增强能力，而不是系统运行的单点故障。

### 7:50～8:30 第八部分：历史诊断书

**屏幕操作**：在 AI 助手页面拖动历史记录范围，点击“生成历史诊断书”。

**讲解**：

> 单次检测适合处理眼前的问题，但运维人员还需要知道问题是否持续存在。因此我设计了历史诊断书。
>
> 用户可以用范围滑块选择多条历史分析记录，系统统计这段时间的样本数、异常数、异常比例、指标均值、最大值、异常次数和日志线索，同时汇总根因与建议。
>
> 这份诊断书不是一张简单的结果卡片，而是对一段时间运行状态的归纳。它帮助用户从“某一刻出了问题”进一步理解“问题是否持续、哪些指标反复异常、应该优先检查什么”。

### 8:30～9:00 第九部分：测试、结果与安全边界

**屏幕**：展示评估结果文件或测试终端截图，再回到网页安全状态。

**讲解**：

> 为了验证系统，我准备了 20 个离线案例，覆盖正常状态、单项指标异常、日志异常和多种异常组合。当前 20 个案例全部判定正确，准确率为 100%。规则异常检测平均耗时约 0.004 毫秒，规则根因分析平均耗时约 0.166 毫秒；自动化测试共 50 项，全部通过。
>
> 这里需要说明，此处数据当前固定测试集上的结果，不代表生产环境中的泛化准确率。规则检测和模型调用的耗时也要分开理解，模型耗时会受到网络和服务状态影响。
>
> 安全方面，系统只采集明确允许的本机资源和项目日志；模型密钥不进入浏览器；所有建议都需要人工确认；自动修复始终禁止。

### 9:00～9:30 结尾：项目价值总结

**屏幕**：回到架构图，或者展示网页中的完整链路状态。

**讲解**：

> 最后总结一下这个项目。它不是把几个独立工具简单拼接起来，而是围绕一次故障建立了一条完整、可解释、可验证的处理链路：Demo 微服务产生指标和日志，Agent 负责采集和协调，规则模块判断是否异常，FreeAiOps 管理异常事件，Agent 取回事件后进行根因分析，LLM 在需要时生成自然语言诊断，网页负责把结果呈现给用户。
>
> 我的个人设计重点体现在统一数据结构、检测与分析分层、FreeAiOps 事件适配、异常去重、安全降级和面向排障的界面设计上。系统当前不自动执行危险操作，强调的是让运维人员更快看到证据、更清楚理解原因，并做出可控的下一步决策。谢谢大家。

## 五、画面安排建议

### 建议保留

- 一张架构图：说明组件关系和数据方向；
- 一张实时监控页面：展示指标、状态、异常信号和事件链路；
- 一张故障检测报告：展示输入指标如何变成检测结果；
- 一张 AI 助手页面：展示历史选择、问题、回答和安全边界；
- 一张历史诊断书：展示时间范围汇总；
- 一张测试结果：展示 20 个案例、准确率和自动化测试通过。

### 不建议出现

- `.env` 文件和任何 API Key；
- 连续数分钟的安装日志或滚屏命令；
- 把 FreeAiOps 说成负责本项目全部异常检测和根因推理；
- 把模型自然语言回答说成已经执行了修复；
- 声称展示了模型的隐藏思维链或内部推理过程。
