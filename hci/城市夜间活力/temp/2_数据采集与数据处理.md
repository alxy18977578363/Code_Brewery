# 数据采集 & 数据处理

## 总体策略
- 双路径数据采集：
  1. Part1：使用 Kaggle / 开源数据集（POI、评论、出租车轨迹等）作为基线数据与样本验证。
  2. Part2：通过爬虫采集 Meituan / 大众点评 的商户、评分与评论，用以补充最新业态与评分信息。
- 合成增强：在隐私或采集不足时，用规则化合成数据（模拟夜间出租车轨迹、评论时间分布）增强时空覆盖。

## 采集实现细节
- Kaggle 数据集：手动/脚本下载并记录来源、版本与检索时间，存放在 `data/synthetic/` 或 `data/` 对应目录。
- 爬虫脚本：位于 `scripts/` 下（例如 `scripts/crawl_dianping_poi.py`）
  - 工具：`requests` + `beautifulsoup4` 或 `selenium`（当页面 JS 渲染必要时）
  - 反爬策略：IP 池（代理）、请求间隔随机化、User-Agent 池、重试与限速
  - 输出：CSV/JSON 格式的商户表（poi_id、name、lat、lon、category、rating、review_count、raw_html/抓取时间）
  - 合规说明：仅抓取公开信息，遵守 robots.txt 与服务条款；若用于真实部署，需法律合规评估。

## ETL 与集成
- 字段映射：设计统一的 POI schema（poi_id, name, lat, lon, category, sub_category, rating, review_count, source, raw_timestamp）并实现映射器。
- ID 归一化：对同一商户来自多个源进行模糊匹配/经纬度近邻合并，生成统一 `global_poi_id`。
- 时间处理：统一时区，夜间时间窗口定义为 `18:00 - 04:00`（可配置），并生成 `night_window` 标签。
- 清洗操作：去重、缺失值策略（重要字段需补足或丢弃）、异常坐标过滤（不在城市边界内）
- 日志与审计：对每次 ETL 保留操作日志（文件或表），包含输入文件、记录数、错误数与运行时长。

## 时空预处理
- 时空栅格化：使用定义好的网格（例如 200m × 200m）或行政单元（街区/商圈）进行聚合。
- 索引：在 MySQL 中对 `lat, lon` 建立空间索引或使用 `ST_GeomFromText` 类型字段；对展示表构建复合索引（`grid_id, date, hour`）以优化查询。

## 指标预计算（数据处理产物）
- 基础聚合表：按 `grid_id` 与 `hour` 聚合的 `poi_count, avg_rating, review_count_sum, taxi_pickups, taxi_dropoffs` 等
- OD 矩阵：夜间时段内的 OD 聚合表（`origin_grid, dest_grid, count, avg_duration`）
- 活力索引草案：权重组合（商户密度、客流量、评论活跃度、营业时间覆盖）生成 `night_vitality_index`

## 可重复运行、后端处理与前端数据交付
- 后端调度与执行：使用任务调度器（Linux `cron` / Windows Task Scheduler / `airflow`）定时执行采集、ETL 与聚合作业，生成分析层与展示层的数据资产。
- 配置集中管理：将关键参数（时间窗口、网格大小、数据源白名单、归一化规则、指标权重）放在后端配置文件（YAML/JSON）或配置服务中，支持版本控制与回滚，保证可复现与可审计。
- 展示层产物：后端定时把聚合结果写入展示级表或导出轻量化 payload（例如 `dashboard_payload.json` 或按接口分片的 JSON），并做好缓存与版本标记，以便前端按需加载。
- 数据传输方式：
  - 静态文件：将 `dashboard_payload.json` 上传到 CDN/S3 或静态目录，前端通过 HTTPS 获取并本地缓存。
  - API 接口：后端提供轻量 REST API（示例：`GET /api/v1/agg?grid_id=xxx&date=2026-04-14&hour=20`）供前端请求具体数据或分页加载大体量聚合。
  - 推送/消息：对于实时告警或异动通知，可由后端通过 WebSocket 或消息队列（如 Redis Pub/Sub）推送到前端仪表盘。
- 接口设计与性能：为常用查询准备汇总接口与聚合缓存，避免前端触发复杂数据库聚合。对大表采用分页、聚合预计算与 TTL 缓存策略，保证前端体验。
- 监控与回滚：后端需记录每次 ETL 与 payload 版本、运行日志与数据量变化；前端在发现异常数据时可回退到历史稳定版本。
- 安全与权限：对 API 添加认证（token）与限流策略，展示层仅暴露必要的聚合数据，原始敏感字段不下发。

示例（后端导出 payload 并供前端使用）：

```json
{
  "version": "2026-04-15T02:00:00Z",
  "grid_summary": [{"grid_id": 123, "date": "2026-04-14", "hour": 20, "night_vitality": 85.6}],
  "top_streets": [{"street": "南京东路街道", "Y_night_vitality": 85.56}]
}
```

后端到前端的明确边界能让前端专注于渲染与交互，后端负责数据质量、聚合性能与合规性。

## 示范 SQL（样例）
- 创建基础聚合表（示例）：

```sql
CREATE TABLE agg_grid_hour (
  grid_id INT,
  date DATE,
  hour TINYINT,
  poi_count INT,
  taxi_pickups INT,
  taxi_dropoffs INT,
  avg_rating FLOAT,
  PRIMARY KEY (grid_id, date, hour)
) ENGINE=InnoDB;
```

- 插入聚合（示例）可以通过 ETL 脚本分批写入或使用 `LOAD DATA INFILE` 加速导入。
