# 数据存储

## 存储架构概览（分层设计）
- 原始层（raw）：存放直接下载/爬取的原始文件（CSV/JSON/HTML 快照），作为审计依据。
- 清洗层（staging）：结构化后的表格数据，字段已统一但保留原始来源字段以便溯源。
- 分析层（warehouse）：经过聚合与预计算的表（例如 `agg_grid_hour`, `od_night`, `poi_master`），供分析与建模使用。
- 展示层（presentation）：为前端定制化的轻量表或导出的 JSON/静态文件（例如 `dashboard_payload.json`），用于快速加载。

## 选择 MySQL 的实现细节
- 表设计：尽量采用合适的主键与复合索引（例如 `PRIMARY KEY(grid_id, date, hour)`），并对大表分表（按日期或网格范围）以控制单表大小。
- 存储引擎：InnoDB（事务、外键支持）；对只读分析表可考虑 MyISAM 或迁移到 ClickHouse
- 空间数据：使用 MySQL 的 `POINT` 类型或 WKT 字符串存储经纬度，并在常用查询字段上建索引。

## 分表与分区策略
- 时间分区：按月或按日分区的聚合表（`agg_grid_hour_2026_04`）便于清理历史数据与并行加载。
- 网格分表：当网格总数非常大时，可按网格 id 范围分表以提升查询性能。

## 数据保管与备份
- 日常备份：每晚增量备份 + 每周全量备份，备份文件存放在外部存储（NAS / S3）
- 恢复演练：定期进行恢复演练，确保备份文件可用性

## 数据接入与 API
- 为前端提供轻量 API：使用 Flask 或简单的静态 JSON 承载展示层数据；API 支持按 `grid_id`、`date`、`hour` 返回聚合数据
- 示例 API 端点：`GET /api/v1/agg?grid_id=xxx&date=2026-04-14&hour=20`

## 权限与合规
- 数据访问控制：在 MySQL 层面设置只读账户给展示服务；敏感源数据（raw html）仅限内部审计访问
- 合规记录：记录每次爬取的时间与来源，保留采集许可或免责声明文档

## 迁移与扩展建议
- 随着数据规模增长，将分析层迁移到 OLAP（ClickHouse）以加速大规模聚合与交互查询
- 将时序/空间密集型指标迁移到专用时序数据库或地理数据库（PostGIS）以提升空间查询效率
